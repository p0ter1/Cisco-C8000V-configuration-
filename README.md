# Cisco C8000V: CUBE для SIP-транка МТС и кластера CUCM

Готовая конфигурация Cisco Catalyst 8000V в роли CUBE (Cisco Unified Border Element) между SIP-транком МТС и кластером Cisco Unified Communications Manager.

| Сторона | Подключение | Транспорт |
|---|---|---|
| МТС | SIP-транк, аутентификация по IP (без регистрации), два SBC | UDP/5060 |
| CUCM | Кластер из двух нод: Subscriber (основная) и Publisher (резервная) | TCP/5060 |

```
  МТС SBC1 / SBC2                                              CUCM SUB (основная)
  198.51.100.10 / .11 ──UDP 5060── Gi1 [ C8000V ] Gi2 ──TCP 5060── 10.10.20.12
                                203.0.113.10   10.10.10.1          CUCM PUB (резерв)
                                                                   10.10.20.11
```

## Требования

- Cisco Catalyst 8000V с IOS-XE **17.9** или новее;
- Smart Licensing: базовый уровень `network-essentials` и сессии CUBE по числу каналов;
- два интерфейса: Gi1 смотрит в сторону МТС, Gi2 во внутреннюю сеть с CUCM;
- CUCM 12.5 или новее (настройки ниже даны для этих версий).

## Логика работы

### Объекты конфигурации

Номера объектов согласованы: всё, что относится к МТС, начинается с `1xx`, к CUCM — с `2xx`.

| Объект | МТС | CUCM |
|---|---|---|
| Тенант (интерфейс сигнализации и медиа) | `tenant 100` → Gi1 | `tenant 200` → Gi2 |
| Распознавание входящих по IP | `uri 100` | `uri 200` |
| Группа серверов | `server-group 100` | `server-group 200` |
| OPTIONS keepalive | `sip-options-keepalive 100` | `sip-options-keepalive 200` |
| Исходящий dial-peer | `100` | `200` |
| Входящий dial-peer | `101` → `dpg 200` | `201` → `dpg 100` |
| Преобразование номеров | `TP-TO-MTS` (исходящие) | `TP-FROM-MTS` (входящие) |

### Прохождение вызова

**Входящий (МТС → CUCM).** INVITE приходит с SBC МТС. CUBE узнаёт его по адресу в заголовке Via (`uri 100`) и выбирает dial-peer 101. Номера приводятся к `+7XXXXXXXXXX`, вызов передаётся в `dpg 200`. Dial-peer 200 отправляет его на Subscriber, а при недоступности — на Publisher.

**Исходящий (CUCM → МТС).** INVITE приходит с любой из нод CUCM (`uri 200`) на dial-peer 201. Он передаёт вызов в `dpg 100`. Dial-peer 100 приводит номера к формату МТС и отправляет вызов на основной SBC, при недоступности — на резервный.

### Принятые решения

- **Защита от мошеннических вызовов (toll-fraud).** SIP принимается только с адресов SBC МТС и нод CUCM (`ip address trusted list`). Остальные пакеты отбрасываются без ответа (`silent-discard untrusted`). ACL на Gi1 дополнительно ограничивает SIP и RTP адресами МТС.
- **Маршрутизация без шаблонов номеров.** Входящий dial-peer однозначно указывает группу исходящих (`destination dpg`). Вызов от МТС всегда идёт в CUCM, от CUCM — всегда в МТС. Петли и случайные совпадения dial-peer исключены.
- **Резервирование.** Обе стороны описаны группами серверов с приоритетом. SIP OPTIONS раз в 30 секунд проверяют каждый сервер, и недоступный исключается заранее, без ожидания таймаута INVITE.
- **Early Offer forced.** CUBE сам формирует SDP в первом INVITE, поэтому на транке CUCM не нужен MTP.
- **Формат номеров.** Внутри CUCM используется `+E.164`. В сторону МТС уходит `7XXXXXXXXXX`, международные номера — с префиксом `810`. Если CUCM передал короткий внутренний номер, в АОН подставляется основной номер организации.
- **Кодеки.** Основной G.711 A-law, резервные G.711 µ-law и G.729. DTMF передаётся по RFC 2833 (`rtp-nte`), факс — по T.38 с переходом на G.711.
- **Переводы вызовов.** REFER и 302 Moved Temporarily к МТС не передаются: переводы и переадресации выполняет CUCM.
- **Скрытие топологии.** Внутренние адреса не выходят наружу (`address-hiding`), служебные заголовки Cisco удаляются SIP-профилем 100.

## Настройка CUCM

1. **SIP Trunk Security Profile**
   - Incoming Transport Type — `TCP+UDP`;
   - Incoming Port — `5060`.
2. **SIP Profile** (создайте копию Standard SIP Profile)
   - Enable OPTIONS Ping to monitor destination status — **включено**;
   - Early Offer support for voice and video calls — `Best Effort (no MTP inserted)`.
3. **SIP Trunk** к CUBE
   - Destination Address — `10.10.10.1`, порт `5060`;
   - Device Pool — с Call Manager Group, в которой есть обе ноды;
   - Run on all Active Unified CM Nodes — **включено**;
   - Media Termination Point Required — **выключено**;
   - DTMF Signaling Method — `RFC 2833` или `No Preference`;
   - Significant Digits — `All`;
   - Calling/Called Party Transformation CSS — чтобы номера уходили в формате `+E.164`.
4. **Маршрутизация**
   - Route Pattern для выхода в город направьте на этот SIP-транк (через Route List).
   - Во входящем CSS транка оставьте только партиции с внутренними номерами (DID). Так вызов от МТС не сможет снова выйти в МТС через CUCM.

## Применение конфигурации

Применяйте конфигурацию по частям в `configure terminal`, в таком порядке:

1. интерфейсы и маршруты;
2. управление (AAA, SSH, NTP, логирование);
3. `voice service voip` и все `voice class`;
4. преобразования номеров и dial-peer;
5. ACL на Gi1 (`ip access-group ACL-WAN-IN in`) — в последнюю очередь.

> **Важно.** Если включить ACL на Gi1 раньше, чем настроены маршруты и доступ к управлению, можно потерять связь с маршрутизатором.

После проверки сохраните конфигурацию:

```
write memory
```

## Вопросы к МТС

Перед подключением уточните у МТС:

- адреса SBC сигнализации и подсети RTP;
- транспорт (UDP или TCP) и порт;
- формат номеров: 10 или 11 цифр, префикс `7` или `8`, формат международных;
- какой номер передавать в From и в P-Asserted-Identity;
- поддерживаемые кодеки, ptime и T.38;
- отвечает ли SBC на SIP OPTIONS. Если нет, удалите строку `voice-class sip options-keepalive profile 100` из dial-peer 100, иначе CUBE будет считать транк недоступным.

```
  10.10.10.13 ──UDP 5060── Gi1 [ C8000V ] Gi2 ──TCP 5060── CUCM PUB 10.97.0.145 (резерв)
                    10.60.112.98   10.97.0.156
```

### Объекты

| Объект | МТС | CUCM |
|---|---|---|
| Тенант (bind сигнализации и медиа) | `tenant 100` → Gi1, `sip-profiles 100`, `asserted-id pai` | `tenant 200` → Gi2 |
| Распознавание входящих по IP (Via) | `uri 100` | `uri 200` |
| Входящий dial-peer | `100` → `dpg 200` | `200` → `dpg 100` |
| Исходящий dial-peer | тот же `100`, `session target 10.10.10.13` | `201`, `server-group 200` (Sub → Pub) |
| Лимит вызовов | `max-conn 16` на dial-peer 100 (вход + выход) | — |
| OPTIONS keepalive | `sip-options-keepalive 100` (UDP) | `sip-options-keepalive 200` (TCP) |
| Преобразование номеров | `FROM_MTS` (rule 110, 111) на входе, `TO_MTS` (rule 120, 121) на выходе | — |
| QoS | `PM-MTS-SHAPER` на выходе Gi1, DSCP EF / CS3 на dial-peer 100 | — |

Маршрутизация идёт **только через dpg**: от МТС вызов всегда попадает в CUCM, от CUCM всегда в МТС, шаблоны номеров не используются. Город, мобильные, международные и экстренные номера отличаются только преобразованием в `translation-rule 120`. Какие номера разрешено набирать, решает CUCM (Route Pattern и CSS).

К МТС используется **один dial-peer 100 на оба направления**. Как входящий он выбирается по `incoming uri via 100` и отправляет вызов в `dpg 200`. Как исходящий он выбирается из `dpg 100`, и тогда его `destination dpg` не используется. Так `max-conn 16` ограничивает **сумму** входящих и исходящих вызовов: на это число рассчитан канал. С отдельными dial-peer на вход и выход лимит считался бы отдельно, и в канал могли бы попасть до 32 вызовов.

Порядок объявления: `201` → `dpg 200` → `100` → `dpg 100` → `200`. Группа может ссылаться только на уже созданный dial-peer, а dial-peer — на уже созданную группу. Иначе при вставке конфигурации целиком группы останутся пустыми и вызовы не пройдут.

### Очистка служебной информации в сторону МТС

`voice class sip-profiles 100` подключён в `tenant 100` и действует на все сообщения, которые CUBE отправляет в МТС: и на запросы, и на ответы. Удаляются:

| Заголовок | Что раскрывает |
|---|---|
| `User-Agent`, `Server` | модель и версию оборудования (`Cisco-CUCM12.5`) |
| `Warning` | внутреннюю диагностику и IP CUBE (`399 10.60.112.98 "No matching outgoing dial-peer"`) |
| `Cisco-Guid`, `Session-ID` | внутренние идентификаторы вызова Cisco и CUCM |
| `Remote-Party-ID` | номер в устаревшем формате Cisco (вместо него используется PAI) |
| `Call-Info`, `Allow-Events` | служебные параметры и события внутренней АТС |

`Reason: Q.850` намеренно не удаляется: по нему МТС корректно обрабатывает отбой. Внутренние адреса в Via, Contact и SDP скрывает `address-hiding`.

### QoS: 16 вызовов G.711 в канале 2 Мбит/с

**Расчёт полосы одного вызова** (G.711, пакетизация 20 мс, 50 пакетов в секунду):

| Составляющая | Байт |
|---|---|
| Голос (RTP payload) | 160 |
| RTP + UDP + IP | 12 + 8 + 20 = 40 |
| Ethernet + FCS | 14 + 4 = 18 |
| **Итого пакет** | **218** |

218 Б × 8 × 50 = **87,2 кбит/с** на вызов (80 кбит/с на уровне IP).
16 вызовов × 87,2 = **1395 кбит/с**, около 70% канала.

**Политика на выходе Gi1** (`service-policy output PM-MTS-SHAPER`):

| Уровень | Класс | Настройка | Зачем |
|---|---|---|---|
| Родитель | `class-default` | `shape average 1900000` | Gi1 гигабитный, а канал 2 Мбит/с. Без шейпера очередь копится у провайдера, и приоритизация на CUBE не работает. 95% — запас на разный учёт заголовков у МТС |
| Потомок | `CM-VOICE-RTP` (DSCP EF) | `priority 1440` | Строгий приоритет на 16 вызовов (1395 кбит/с) плюс ~3% на RTCP. 17-й вызов в эту полосу уже не помещается |
| Потомок | `CM-VOICE-SIP` (DSCP CS3, AF31) | `bandwidth 128` | Гарантия для сигнализации: одновременные INVITE не теряются при загрузке голосом |
| Потомок | `class-default` | `fair-queue` | Всё остальное (ICMP, служебный трафик) |

**Разметка.** Dial-peer 100 метит голос к МТС как EF (`ip qos dscp ef media`), а SIP как CS3 (`ip qos dscp cs3 signaling`). Класс SIP дополнительно принимает AF31 — значение CUBE по умолчанию.

**Ограничение числа вызовов.** `max-conn 16` на dial-peer 100 не пускает 17-й вызов ни в одну сторону: CUBE отвечает отказом сразу, а не делит полосу и не ухудшает качество уже идущих разговоров. `mode border-element license capacity 16` приведён в соответствие.

**Чего QoS на CUBE не может.** Входящий поток от МТС к CUBE приоритизирует сам МТС. С CUBE он ограничен тем же `max-conn 16`, то есть не превысит те же 1395 кбит/с. Если по каналу идёт не только голос, попросите МТС включить приоритизацию EF на их стороне.

Проверка после включения:

```
show policy-map interface GigabitEthernet1 output   ! счётчики классов, drops в CM-VOICE-RTP должны быть 0
show dial-peer voice 100 | include maxConn|DSCP
show call active voice brief                        ! tos 0xB8 (EF) на медиа-ноге к МТС
```

### Что сделать до включения

- заменить `<PASSWORD>` на свои пароли; RSA-ключ сгенерировать отдельной командой `crypto key generate rsa modulus 2048` до вставки конфига;
- узнать у МТС адреса медиа-серверов RTP и добавить маршрут через WAN (в конфиге оставлена закомментированная строка);
- уточнить формат исходящих номеров (`translation-rule 120`, `121`). Входящие МТС присылает в 10-значном формате, исходящие сейчас уходят в 11-значном (`7XXXXXXXXXX`);
- после включения проверить `show voice class sip-options-keepalive 100`. Если SBC МТС не отвечает на OPTIONS, dial-peer 100 уйдёт в busyout и вызовы через МТС перестанут работать;
- на CUCM: SIP Trunk на `10.97.0.156` (TCP), Route Pattern в город, CSS транка с партицией DN 2030.

### Debug с площадки

Debug входящего вызова (МТС → CUBE → CUCM, на внутренний `2030`) показал:

- CUCM ответил `404 Not Found` (`No matching outgoing dial-peer`). Причина была на стороне АТС и уже исправлена;
- в ответе, ушедшем в МТС, были `Server: Cisco-CUCM12.5`, `Warning` с IP CUBE и `Session-ID`. Теперь их удаляет `sip-profiles 100`;
- МТС присылает номера в 10-значном формате, правила 110 и 111 его обрабатывают.

| # | Проблема | Исправление |

| 1 | Входящий вызов на чужой номер (например, `74951234568`) мог уйти обратно в МТС: петля, платный транзит | Маршрутизация только через dpg: от МТС → только CUCM |

### Ревью конфигурации

После добавления QoS конфиг площадки отдельно проверен на корректность (без устройства). Критичных проблем не найдено. Расчёт полосы и синтаксис иерархической политики (шейпер + LLQ + CBWFQ) подтверждены.

| Замечание | Что сделано |
|---|---|
| Кириллица в `description` класса QoS: IOS может её исказить или отвергнуть | Заменена на ASCII (кириллица осталась только в комментариях `!`) |
| `hunt-scheme preference` в server-group может не поддерживаться | Удалён: выбор по `preference` и так поведение по умолчанию |
| Пароли задавались как `secret` (тип 5) | `algorithm-type scrypt secret` |
| SSH доступен со стороны МТС, настроены только `vty 0 4` | `vty 0 15`, `access-class ACL-MGMT` (только LAN `10.97.0.0/24`), `exec-timeout` |
| `crypto key generate rsa` внутри вставляемого конфига съедает следующие строки | Вынесен в отдельную команду до вставки |
| Нет ACL на Gi1 и маршрута к медиа-серверам МТС | **Не сделано:** нужны адреса медиа-серверов МТС, без них ACL отрежет голос |
| При превышении `max-conn` вызывающий, вероятно, получит 503, а не «занято» | Оставлено. Попросите МТС ограничить транк 16 каналами на их стороне |
